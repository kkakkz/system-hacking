## 왜 메모리가 필요한가
- 레지스터는 CPU 바로 옆에 있어야 해서 비싸고 개수가 적다. 반면 메모리는 훨씬 크지만 느리다. 
그래서 "지금 당장 CPU가 연산해야하는 것"은 레지스터에, "많은 양의 데이터"는 메모리에 저장한다.

## 메모리 주소 체계
- 레지스터는 개수가 적어서 `rax`, `rbx` 처럼 이름으로 부르지만, 메모리는 위치가 너무 많아서 **번호(주소)**로 구분한다.
각 주소는 딱 **1바이트**를 가리킨다. 

## 스택(Stack)
### push/pop
  - push : 값을 스택 맨 위에 쌓는다
  - pop : 스택 맨 위 값을 꺼내서 레지스터에 넣는다 (LIFO - 마지막에 넣은게 먼저 나옴)
### 스택은 거꾸로 자란다 
```
rsp = 0x...050  (여기에 cool cats가 있음)
push boba_cafe  → rsp가 0x...048로 감소 (8만큼 감소)
                → boba_cafe는 0x...048에 저장됨
```
스택은 높은 주소에서 낮은 주소 방향으로 자란다. `push` 할 때마다 `rsp`가 8만큼 감소하고, `pop` 할 때마다 8만큼 증가한다.
**왜 핵심이냐?** : 이게 BOF의 심장이다. 스택이 "높은 주소->낮은주소"로 자란다는 걸 모르면, 왜 버퍼를 넘치게 써서 "위쪽(더 높은 주소)에 있는" 리턴 주소를 덮어쓸 수 있는지 이해가 안된다.

### pop해도 데이터는 남아있다.
- `pop`은 사실 데이터를 지우는게 아니라, "스택의 끝(top)이 어디인지"를 가리키는 `rsp`값만 바꾸는 것이다. 실제 바이트는 메모리에 그대로 남아있다.
이건 나중에 "스택에서 이미 pop된 값도 여전히 읽을 수 있다."는 사실과 연결된다.

## 메모리 접근 문법 : 대괄호 `[]`
```assembly
mov rax, 0x12345    ; rax에 주소값 0x12345를 넣음 (아직 메모리 접근 아님)
mov rbx, [rax]       ; rax가 "가리키는" 메모리 주소에서 값을 읽어서 rbx에 저장 (메모리 접근!)
```
대괄호 `[]`가 핵심 문법이다 : `rax`처럼 대괄호 없이 쓰면 "그 레지스터 값 자체"를 의미하지만, `[rax]`처럼 대괄호로 감싸면 "그 값을 주소로 취급해서, 그 주소에 있는 메모리 데이터를 읽어라"는 뜻이 된다.
`rbx`가 64비트 레지트서니까 8바이트를 읽어온다.
#### 포인터 (pointer)란
> "레지스터에 담긴 값이 어떤 메모리 주소를 가리키고 있을 때, 그 레지스터가 그 메모리를 포인트(point)한다고 말한다."
`rax`에 주소값이 들어있고 그걸 `[rax]`로 참조하면, 그 메모리의 포인터다. 이게 "포인터"라는 용어의 전부이다. - C언어 포인터 개념이 바로 여기서 나온 것이다.

## `rsp`로 직접 메모리 접근 (push의 정체)
```assembly
sub rsp, 8
mov [rsp], rax
```
이건 사실상 `push rax`와 완전히 동일한 동작이다. `push`는 결국 "rsp를 8줄이고, 그 자리에 값을 쓰는"걸 한 명령어로 압축해 놓은 것 뿐이다.
이거러 알면 나중에 "push 명령어가 없어도 스택을 직접 조작"하는 어셈블리를 이해할 수 있다.

## 부분 레지스터로 쓰기 크기 조절
```assembly
mov [0x1337], ebx  ; ebx(32비트, 4바이트)만큼만 메모리에 씀
mov [0x1337], bh   ; bh(8비트, 1바이트)만큼만 씀
```
레지스터 크기 계보 (al/ax/eax/rax)를 그대로 활용해서 메모리에 몇 바이트를 쓸지 조절할 수 있다. 여기서도 지난번 배운 "eax에 쓰면 rax 상위 32비트가 0으로 초기화된다"는 규칙이 나온다.

## 리틀 엔디안 (Little Endian)
```text
rax = "cool cats" 라는 값을 8바이트 메모리에 쓰면 . . .
메모리에는 바이트 순서가 거꾸로 저장됨 (예: 's' 't' 'a' 'c' ' ' 'l' 'o' 'o' 'c' 순서)
```
여러 바이트를 한 번에 읽고/쓸 때, 바이트 순서가 거꾸로 저장된다. 이게 유명한 little endian이다.
**중요** : 바이트 순서만 뒤집히고, 바이트 안의 비트 순서는 그대로이다. 그리고 이건 "여러 바이트를 레지스터 <-> 메모리 간에 옮길 때"만 발생한다.
**왜 핵심이냐?** 나중에 GDB에서 메모리 덤프를 볼 때, 또는 익스플로잇 페이로드에서 주소값을 바이트 배열로 만들 때( `p64()` 같은 pwntools 함수), 리틀 엔디안 순서로 안 바꾸면 페이로드가 완전히 틀어진다.

## 주소 계산 (Address Calculation)
```assembly
mov rbx, [rsp + rax*8]
```
`레지스터 + 레지스터*(2, 4, 8 중 하나) + 상수` 형태로 주소를 계산할 수 있다. 배열이나 구조체 접근할 때 이 패턴이 쓰인다. (`rax`를 인덱스 처럼 쓰는 것)

## LEA (Load Effective Address)
```assembly
lea rdx, [rip + 5]
```
`lea`는 `[]`안의 주소를 계싼만 하고, 그 계산 결과 자체를 레지스터에 저장한다. (메모리를 읽지 않음. `mov [rax], ...` 처럼 실제 메모리 접근이 아니라, "주소 산수 계산기"로 쓰는 것)
그리고 `lea`는 특별하게 `rip`(다음 실행될 명령어 주소)에 **직접 접근 가능**한 유일한 방법 - `mov`로는 `rip`값을 못 가져온다.

## 즉치값을 메모리에 쓸 때 크기 명시
```assembly
mov dword ptr [rax], 0x1337
```
`mov [rax], 0x1337`만 쓰면 어셈블러가 "몇 바이트를 쓸지" 모호해서, `byte/word/dword/qword ptr`로 크기를 명시해야 한다. 셸코딩할 때 자주 마주치는 문법이다.

## 스택 외 다른 메모리 영역 존재
스택 말고도 코드 영역(rip-relative로 접근), 힙(heap), 기타 OS영역 들이 있다.
